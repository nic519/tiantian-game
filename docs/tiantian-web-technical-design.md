# 甜甜爱消除 Web 复刻技术方案

日期：2026-11-12  
状态：技术设计，尚未实施产品代码  
目标平台：手机浏览器、微信内置浏览器、桌面浏览器

## 1. 结论与建议

可以使用 Web 技术重做。推荐采用 **TypeScript + Vite + Phaser**，先交付“视觉尽量贴近原作、主棋盘能够持续游玩、刷新后可以继续”的独立浏览器版本。

首先分析现有小游戏包与本地缓存，得到界面资源清单、物品合成链、订单和生产规则；再编写独立的游戏状态与渲染代码。原包是构建产物，不能当成完整 Cocos Creator 工程直接重新导出。

本方案默认的首版范围由方案作者提出：主棋盘、生产、二合升级、订单、基础奖励、体力、简化成长、本地存档。原作完整剧情、全部地图、活动和商业化体系属于后续扩展，不计入首版。对尚未核实的细节明确标为待核实；需要先观察原游戏和核对配置，再冻结对应规则。

## 3. 是否需要 REA，以及它放在哪一步

[morluto/rea](https://github.com/morluto/rea) 是面向 Agent 的逆向分析工具集，支持 JavaScript 应用的结构分析与后续特性追踪。它可辅助理解构建脚本，但不应把它当成小游戏的一键复刻器。

我查看的官方介绍和 JavaScript 工作流没有明确给出微信 `.wxapkg` 专用解包能力。这个项目应先使用微信包专用解析，再把解出的 JavaScript 作为 REA 的输入。是否能充分识别当前 Cocos 构建产物，要用一个实际业务模块验证。

| 工作 | 首选方法 | REA 的位置 |
| --- | --- | --- |
| 解开 V1MMWX，读取包内文件 | wxapkg 专用解析器，带包头、偏移、长度校验 | 前置步骤，不依赖 REA |
| 找回文件、资源路径与缓存对应关系 | Cocos bundle 配置 + cacheList + 专用映射脚本 | 辅助查看模块关系 |
| 识别场景、物品、订单、体力模块 | 格式化后的业务 JS、配置和行为观察 | 值得试用静态分析、字符串或模块种子追踪 |
| 确定合成、扣体力、发奖励的规则 | 配置核对 + 关键函数阅读 + 原作操作案例 | 追踪结果作为证据，不能替代实际验证 |
| 理解未出现在客户端的服务端规则 | 自建简化规则，明确差异 | 无法凭空恢复缺失实现 |
| 浏览器渲染、交互、存档、部署 | 重新编写 Web 游戏 | REA 不负责完成这些工作 |

REA 为可选分析依赖，不进入浏览器运行依赖。先用小范围分析判断收益；如果 Cocos 自定义模块加载方式导致关系图不完整，则使用包内模块注册名、调用位置和人工核对继续分析，不阻塞实施。

建议只分析主业务脚本与有关配置，避免把 SDK、引擎和海量活动一起纳入首次分析。当前任务没有安装 REA、修改 MCP 设置或运行原包；正式使用时锁定工具版本并记录分析输入摘要。

## 4. 实施前的素材与行为调查

### 4.1 产出四份可核查清单

1. 资源清单：逻辑路径、bundle、UUID、文件哈希、大小、格式、是否存在、替代资源。
2. 玩法清单：触发动作、前置条件、状态变化、动画、音效、边界行为、证据来源。
3. 页面清单：加载、主界面、主棋盘、订单、物品信息、仓库、设置、奖励、简化成长。
4. 差异清单：已忠实核实、首版简化、缺少资料、后续实现。

每个规则标注“包内实现 / 配置 / 原作观察 / 本方案默认值”，避免把推断写成原作事实。随机掉率如果只有少量观察，不声称已恢复精确概率。

### 4.2 包体与缓存处理

读取缓存副本，保留来源与哈希；原微信目录保持只读。解析文件索引时校验偏移、尺寸、输出路径，避免覆盖原文件或目录穿越。

建立 `逻辑路径 → UUID → import/native → 缓存物理文件 → Web 资源` 的映射。需要同时处理构建 JSON 中的 SpriteFrame、图集旋转、裁切区域、原始尺寸、锚点和九宫格边框，不能只提取 PNG 后丢掉坐标数据。

优先使用 PNG/JPEG 等浏览器可用素材。ASTC 不能作为统一可用格式：有 PNG 副本则采用副本，只有压缩纹理则先验证离线转换与透明通道。动画若依赖特定 Spine/DragonBones 版本，先检查数据与播放器兼容性，首版允许用精灵序列或补间实现同等反馈。

首版资源缺失分两类：阻断主棋盘交付的必须补齐或制作替代品；后续剧情、活动资源不阻塞首版。不能根据资源索引推断所有资源已经下载。后续仅为选定首版范围补齐文件，保留缺失报告，不全量镜像原厂资源服务。

包内第三方 SDK、生产服务地址、上报和凭据不进入新项目。原作美术、音频的复用以可用授权范围为准；需要发布的版本通过资源 manifest 切换为可发布素材，核心逻辑不受素材替换影响。

### 4.3 原作行为基准

记录新手到订单完成的一段连续操作：进入棋盘、点击生产、拖到空位、同物品合成、不同物品拖放、最高级物品、无效区域松手、棋盘满、体力不足、订单重复需求、领取奖励、仓库移入移出、切后台恢复。

记录屏幕尺寸、棋盘行列与坐标、关键界面截图和短视频时间点。棋盘行列、交换行为、锁定格解锁方式与合成奖励必须先核实，不能按“三消游戏”的经验填入。当前推定属于二合与订单成长玩法，精确规则以此次调查为准。

## 5. 三条技术路线

| 路线 | 优点 | 成本与边界 | 本项目选择 |
| --- | --- | --- | --- |
| 原 Cocos 工程导出 Web | 有完整工程时，场景、动画、预制体复用最多 | 目前只有构建包；恢复工程、兼容旧引擎和替换微信依赖的成本不确定 | 获得完整工程时优先重新评估 |
| TypeScript + Phaser 重做 | 渲染、拖拽、场景、补间和音频由同一游戏框架组织，适合独立 H5 | Cocos 资源元数据需转成自己的格式，规则和 UI 需要重建 | **默认推荐** |
| React + DOM/CSS 重做 | 界面表单容易开发，最初可玩原型快 | 棋盘、特效、音频、拖拽和布局需自行协调，复杂后维护成本上升 | 适合低动效验证版本 |

推荐技术组合：TypeScript、Vite、Phaser、IndexedDB（可用轻量 idb 封装）、Vitest、Playwright。实施时选择并锁定通过兼容性验证的 Phaser 版本；本方案不假设所有主版本的 API 完全相同。

首版不强制引入 React。主棋盘、订单 HUD 和游戏弹层统一在游戏渲染层绘制，减少 DOM 与 Canvas 之间的位置及事件同步。浏览器加载失败提示、存档导入导出和开发工具采用 DOM；如以后需要较多管理页面，再引入 React。

本项目当前没有 SEO、服务端渲染或账号接口需求，所以首版使用静态构建。若以后加入 Next.js 门户，游戏仍可作为独立客户端模块或独立路径接入。

## 6. 首版功能边界

首版目标是完成一个可重复、可持续的循环：生产物品 → 移动整理 → 同级二合升级 → 满足订单 → 领取奖励 → 解锁或升级内容 → 再次生产。

| 功能 | 首版交付 | 验收依据 |
| --- | --- | --- |
| 加载与主界面 | 加载反馈、开始/继续、基础场景切换 | 能进入棋盘，失败可重试 |
| 主棋盘 | 配置化行列、初始格、空格、物品、锁定状态 | 布局与选定原作基准一致 |
| 生产 | 点击生产器、消耗体力、掉落、冷却、满盘提示 | 失败不扣资源、不推进随机状态 |
| 合成 | 拖拽、合法性校验、升级反馈、合成链提示 | 规则匹配基准，无复制或丢失 |
| 订单 | 需求展示、物品检查、提交、奖励、新订单 | 完成后有可继续追求的目标 |
| 基础成长 | 经验/等级，有限解锁，至少一次成长展示 | 明确标为简化流程，不冒充完整剧情 |
| 仓库 | 有限容量，移入与取出 | 与棋盘共用同一物品实例规则 |
| 体力 | 消耗、上限、按时间恢复、恢复提示 | 刷新与后台返回结果一致 |
| 设置 | 音乐、音效；存档导出/导入 | 设置持久化，音频符合浏览器交互要求 |
| 存档 | 自动保存、版本校验、上一有效快照 | 关闭并重新打开后继续 |

首版建议内容预算：3 条物品链，每链约 6–8 级，2 类生产器，20 个经过可达性验证的订单模板，1 组有限成长任务。此为工作量默认值，不是原游戏规模；素材短缺时由原创或占位素材补齐，并在差异清单记录。

首版不接原游戏账号、支付、广告和服务器；不复刻完整运营活动、排行或全部地图。离线本地进度与微信里的原存档相互独立。

## 7. 游戏代码架构

采用单项目、清晰分层，避免一开始拆成多包工程。

| 目录 | 职责 | 依赖约束 |
| --- | --- | --- |
| `src/game/domain/` | 棋盘、物品、生产、合成、订单、奖励、体力 | 纯 TypeScript，不引用 Phaser、DOM 或 IndexedDB |
| `src/game/config/` | 物品、生产器、订单、初始棋盘、成长配置与校验 | 静态数据，启动前验证 |
| `src/game/scenes/` | Boot、Preload、Home、Board 场景 | 将输入转为命令，订阅结果 |
| `src/game/view/` | 棋子、订单卡、HUD、弹层、动画、音效 | 只呈现状态，不私自发放奖励 |
| `src/game/runtime/` | 会话、命令队列、随机源、时钟、状态发布 | 协调领域层与适配器 |
| `src/game/adapters/` | 存档、音频生命周期、资源路径等浏览器适配 | 可替换实现 |
| `src/shell/` | 页面容器、异常提示、导入导出 | 不管理棋盘物品状态 |
| `public/assets/` | 首版允许使用的图片、图集、声音 | 由 manifest 引用 |
| `tools/` | 资源清点、映射和配置转换工具 | 不随游戏分发原始包或 SDK |

输入经统一命令入口处理：读取当前状态 → 校验 → 计算完整变更 → 原子提交状态 → 安排持久化 → 根据事件播放动画。渲染中断不影响已经提交的奖励或物品归属。

拖拽中的坐标仅属于视图；松手合法时才提交领域变更。每个命令有 ID，旧 revision 的输入会重新验证或拒绝，不能靠动画回调决定是否发奖励。

## 8. 数据与核心规则

### 8.1 最小数据模型

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| ItemDefinition | id、chainId、level、nextId、assetKey、capabilities | 可否合成/移动/生产由能力与配置决定 |
| ItemInstance | instanceId、definitionId、producerState | 实例 ID 唯一；生产器剩余次数、批次、冷却时间必须持久化 |
| Cell | index、accessState、itemInstanceId | 格子开放/锁定与物品定义分开 |
| ProducerDefinition | dropTable、energyCost、cooldown、batchSize | 掉落权重与节奏配置化 |
| Order | id、requirements、rewards、status、templateId | 重复物品需求按数量统计 |
| Player | level、xp、coins、gems、energy、energyAnchor | 货币使用整数，能量恢复时间有统一锚点 |
| SaveEnvelope | schemaVersion、contentVersion、revision、savedAt、state | state 包含棋盘、仓库、订单、成长、随机源和已处理命令信息 |

### 8.2 合成与移动

相同可合成物品、未受锁定或其他状态阻止、存在 nextId 时，消耗源和目标两个实例，在目标格生成升级实例，源格变空。最高级物品不能继续合成。

不同物品之间是否交换位置、箱子/冰冻/气泡等特殊状态是否可交互，必须根据调查结果形成规则矩阵。首版只实现矩阵中明确列出的状态，后续活动道具不混入通用合成函数。

无效松手回到原位置，不扣体力，不修改订单。仅对正在操作的棋子锁定输入；首版最多允许一个有效拖拽指针，避免多指同时合成同一实例。

### 8.3 生产与体力

生产前同时校验：生产器状态、体力、冷却、剩余次数和可用空位。只有全部满足才抽取掉落、扣体力、更新生产器并生成物品。抽样随机源由状态维护，可复现，同一失败命令不消耗随机序列。

使用绝对时间计算冷却与体力恢复，不能把 setInterval 执行次数作为真实流逝时间。若达到体力上限，恢复锚点随规则正确重置，避免先前累计时间使下一次消耗瞬间补满。时钟回拨时恢复增量按 0 处理；本地单机不承诺抵抗修改系统时间。

### 8.4 订单与持续游玩

提交订单时先匹配可用实例并排除锁定物品，同一个实例不能抵扣两个需求；再一次性消耗、标记完成并发放奖励。重复提交同一订单不会再次获得奖励。

20 个模板可按成长阶段循环抽取；每次生成前依据已解锁生产器与完整合成链检查可达性。首版保持少量活跃订单，完成后补充，不在有限订单结束后陷入无目标状态。全部成长演示结束后进入明确标识的自由经营阶段。

### 8.5 本地存档

IndexedDB 保存完整领域状态，设置可放入同一数据库；无需保存动画和拖拽坐标。每次有效命令后排队保存对应 revision，同一写入器按序处理，不允许较旧快照覆盖较新快照。关键订单与奖励操作落盘完成后再显示已保存状态。

保存失败时保留内存进度并提示可导出，不能静默宣称已保存。页面隐藏时做一次尽力保存，但不把它当成可靠的唯一时机。启动先校验结构、内容版本与物品引用，失败时尝试上一有效快照并提示；保留原坏档供导出，不自动清空。

schemaVersion 负责格式迁移；contentVersion 对应规则和素材版本。导入需校验尺寸、物品 ID、数量和引用关系。多标签页默认只允许一个写入会话，其他标签页只读或提示切换，避免互相覆盖。

## 9. 视觉、交互和资源加载

### 9.1 还原方式

先冻结一组基准画面：主界面、主棋盘、物品说明、订单完成、仓库、设置。按照背景、布局、图标、字体、九宫格、动画、音效逐层校准。

原作字体不可用时提供替代字体，并记录文字宽度、换行差异。需要重绘的背景与图标统一美术风格，不用大量 emoji 替代正式棋子。主棋盘完整交互先于活动页面数量。

### 9.2 统一布局

基准分辨率从原作场景 Canvas 配置和截图核实后确定，不预设某个尺寸是原作事实。使用一套逻辑坐标映射到屏幕坐标，棋盘与弹层复用相同布局规则。

手机适配可见视口与 safe area，顶部 HUD、订单、棋盘、底部操作区有各自最小空间；短屏可压缩装饰区，不能遮挡棋盘或关键按钮。桌面保持竖屏舞台居中，两侧留背景，避免棋子在宽屏被拉成矩形。横屏显示竖屏舞台，不依赖强制锁屏。

使用 Phaser Scale Manager 统一缩放，浏览器大小或地址栏高度变化后重新校准输入坐标。Canvas 区域限制默认触摸滚动，DOM 设置面板仍可正常滚动。特效、奖励飞行和弹层始终不得撑出横向滚动条。

### 9.3 加载与性能

资源按加载界面、主棋盘、成长页面分组。首个可玩包只包含必要棋子、UI、背景和声音；不把 34,034 条资源索引全部塞入首屏。缺失关键资源提供重试，非关键音效可降级静音。

渲染优先 WebGL；关闭不需要的物理引擎与高成本效果。棋子与粒子复用，预合并图集，按设备限制 DPR，切后台暂停渲染与音频。恢复后用领域时钟补算体力，不逐帧补播离线过程。

音频在首次有效用户手势后解锁；Safari 或微信内置浏览器拒绝播放时允许静音继续，并在下一次手势重试。

以下为待实测的首版预算，不是已经通过的指标：

| 指标 | 目标与测量方式 |
| --- | --- |
| 首次可玩传输量 | 目标 ≤ 5 MB，压缩后且不含延迟加载内容；阶段 0 结束按实际素材重新确认 |
| 首次可玩时间 | 10 Mbps、100 ms RTT、冷缓存、非调试构建下目标 ≤ 8 秒 |
| 流畅度 | 指定目标手机，连续 60 秒典型操作平均 ≥ 55 FPS；记录 P95 帧耗时与长任务 |
| 交互反馈 | 拖拽跟手、无效松手回弹、合成反馈各有固定基准录屏，人工对照 |
| 稳定性 | 典型 20 分钟游玩、切后台、刷新恢复无状态错误；观察内存是否持续增长 |
| 布局 | 320/375/390/430 CSS px 宽度及桌面窗口下，无横向滚动与按钮遮挡 |

## 10. 部署与后续服务端

首版运行在普通静态 HTTPS 托管上，构建产物为 Vite 的 dist。配置与素材同源提供，资源采用内容哈希长缓存，入口 HTML 短缓存；一次发布使用完整内容版本，避免新配置配旧素材。

不立即加入 Service Worker，减少原型阶段缓存旧版本的调试成本；后续若需要离线可玩，再加入版本化预缓存与明确更新提示。保留存档导出入口，不能把浏览器本地存储当成永久云备份。

如果后续需要跨设备存档、排行榜或真实支付，再增加独立 API 和账号系统。可以选熟悉的 Go 服务，也可以用轻量 JavaScript 服务；这一选择不影响当前核心规则与渲染层。涉及排行或有价值奖励时，生产、合成、奖励和订单均需服务器校验，不能只上传客户端最终货币值。

## 11. 实施阶段、交付物与验收

工作量是“单名熟悉 TypeScript 的开发者，素材大部分可用”的工程估算，不是承诺日期；需要原创美术或大量素材修复时另计。

| 阶段 | 主要工作 | 阶段交付 | 粗估 |
| --- | --- | --- | --- |
| 0：证据与资源 | 包体清点、缓存映射、关键规则核对、界面基准、REA 小样验证 | 资源缺失报告、玩法矩阵、3 条合成链、首版范围冻结 | 1–2 人日 |
| 1：可玩棋盘 | 工程、场景、物品、拖拽、生产、合成 | 占位或可用素材下核心交互可玩 | 2–4 人日 |
| 2：完整循环 | 订单、奖励、体力、仓库、成长、本地存档 | 完成多轮订单并可刷新继续 | 3–5 人日 |
| 3：视觉与兼容 | 真实界面、图集、动画音效、移动适配、性能 | 选定基准页面对照版、真机报告 | 3–5 人日 |
| 4：交付 | 边界回归、构建、静态部署说明、差异记录 | 可部署构建及说明 | 1–2 人日 |

首版合计约 10–18 人日；完整原作规模无法根据这 5 个包可靠估算。阶段 0 若发现主棋盘素材或配置大量缺失，调整内容预算与排期，再进入依赖这些结果的开发。

### 11.1 必须验证的领域用例

- 合法/非法合成、最高级物品、锁定格、跨出棋盘、多指干扰。
- 满盘/体力不足/冷却时生产不扣体力、不消耗次数、不推进随机源。
- 订单的重复需求、重复提交、多个订单争用相同实例。
- 体力到上限、离线恢复、跨日期、系统时钟回拨。
- 生产器状态、仓库、随机源在刷新恢复后保持一致。
- 存档结构迁移、坏档回退、写入失败、导入非法引用、多标签页冲突。

规则用 Vitest 测试，不测试与实现完全相同的空壳封装。Playwright 验证浏览器流程与关键截图；WebKit 自动化不能替代 iPhone Safari 与微信内置浏览器真机验证。

### 11.2 首版最终验收

用户能够在手机打开游戏、完成至少 3 个不同订单、获得奖励并经历一次成长，再关闭页面并继续相同进度。棋盘不出现复制、丢物品或重复奖励；网络请求不依赖原厂账号、生产 API 或 SDK；选定界面具备可逐项比对的视觉差异记录。

交付源代码、锁定依赖、构建说明、内容配置、资源 manifest、差异清单和验证报告。原始微信包与用户微信数据不随交付分发。

## 12. 下一步的明确选择

建议批准的方向是：**保留“解析原包辅助理解”这一步，使用 Phaser 重写独立 H5，先还原主棋盘与完整单机循环。REA 作为可选静态分析助手。**

进入实施后的第一个成果应是资源和行为调查结果，而非先画一个没有验证过玩法的普通三消页面。如果后续拿到了原始 Cocos 工程，再基于实际可构建性决定是否改走原引擎导出路线。
